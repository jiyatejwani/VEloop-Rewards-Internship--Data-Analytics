# VELOOP Rewards | Product Analytics & Data Readiness Blueprint

**Data Analyst Internship — Task 01**  
**Author:** Jiya Tejwani

> **Data Disclaimer:** All datasets used in this project are simulated and fictional. The findings do not represent actual VELOOP users, earnings, withdrawals, revenue, retention, or business performance.

## Project Overview

VELOOP Rewards is a rewards and engagement product concept that requires a reliable analytics foundation before meaningful production analytics can be performed.

This project focuses on assessing the available data, identifying data quality and coverage gaps, defining business KPIs, and designing an analytics framework to support future product decisions.

The project combines Python-based data profiling, SQL KPI definitions, an interactive dashboard, and structured documentation to evaluate analytics readiness and outline the steps required for implementation.

## Business Problem

Reliable product analytics depends on consistent identifiers, complete event tracking, well-defined metrics, and structured transactional data.

The supplied datasets do not contain all the information required to measure the complete rewards and monetization lifecycle. The project therefore investigates what can be verified using the available simulated data and what needs to be implemented before production reporting becomes reliable.

## Project Objectives

- Profile the supplied datasets and understand their structure.
- Assess data quality, completeness, and referential integrity.
- Identify gaps in the existing analytics infrastructure.
- Define KPIs for user activity, rewards, wallets, withdrawals, and referrals.
- Design a logical data model and event-tracking plan.
- Build an interactive dashboard to communicate analytical findings.
- Develop documentation and implementation recommendations for future analytics readiness.

## Key Findings

### 1. User Identity and Data Integration

The two supplied workbooks use similar-looking user ID formats, but matching IDs do not identify the same individuals across the files. The audit found zero matching identities among 1,000 shared ID values.

Consequently, the IDs cannot safely be used as a common user key without a verified identity-mapping mechanism.

### 2. Missing Monetization Data

The supplied datasets do not contain the transactional tables needed to fully analyse the rewards and monetization lifecycle, including rewards ledgers, wallet transactions, withdrawals, and referral lifecycle records.

No monetary amount field was identified in the supplied datasets.

### 3. KPI Readiness

The project sampled 20 KPIs and found that only 7 were computable from the available simulated data. Other metrics require additional data structures, engineering validation, or implementation.

These findings highlight why data availability and metric definitions must be validated before business performance is reported.

## Getting Started

### Prerequisites

- Python 3.9 or later
- pip
- A modern web browser

### 1. Clone the Repository

```bash
git clone https://github.com/YOUR-USERNAME/VELOOP-Task-01.git
cd VELOOP-Task-01
```

Replace `YOUR-USERNAME` with your GitHub username and adjust the repository name if necessary.

### 2. Run the Dashboard

Open `index.html` directly in your browser.

The dashboard uses the precomputed metrics in `data.js`; no frontend build step is required.

### 3. Install Python Dependencies

```bash
cd analysis
pip install -r requirements.txt
```

### 4. Run the Analysis

Run the scripts from the `analysis/` directory:

```bash
python 01_profile_datasets.py
python 02_data_quality_audit.py
python 03_build_dashboard_data.py
```

The scripts profile the datasets, assess data quality, and regenerate `data.js` for the dashboard.


### 5. Explore the SQL Queries

Review `sql/kpi_queries.sql` for KPI definitions and queries. Metrics dependent on unavailable transactional data are identified as proposed rather than treated as verified business results.

## Data Integrity and Limitations

- All supplied data is simulated and fictional.
- Similar user IDs across the two workbooks must not be assumed to represent the same individuals.
- Metrics that depend on unavailable tables cannot be validated from the current datasets.
- Proposed KPIs and data structures require engineering implementation and verification.
- Dashboard findings should not be interpreted as actual business performance.
